# Hulu support agent

A customer-support agent for one brand's public Twitter stream, built from
[Customer Support on Twitter](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter)
(~3M tweets), plus the evaluation needed to decide whether to trust it.

For every incoming message the agent does three things: **classifies** it into one
of ten intents induced from the data, **drafts a reply** grounded in how Hulu has
actually resolved similar issues before, and **decides** whether it can be
auto-handled or needs a human, with a stated reason.

## Results

Intent classification, on the 120-item uniform-random evaluation slice. Intervals
are 95% bootstrap.

| system | agreement | 95% CI | macro F1 | escalation precision | escalation recall |
|---|---:|---:|---:|---:|---:|
| majority class | 20.8% | 14.2–28.3 | 0.034 | 0.0% | 0.0% |
| keyword + copy nearest reply | 40.0% | 30.8–49.2 | 0.364 | 61.9% | 28.9% |
| **agent** | **77.5%** | 70.0–85.0 | **0.707** | 72.7% | 35.6% |

Reply quality, scored blind by a judge model from a different vendor.

| system | grounded | actionable | safe | voice | mean | postable |
|---|---:|---:|---:|---:|---:|---:|
| majority class | 2.56 | 3.80 | 4.92 | 3.34 | 3.65 | 90.0% |
| keyword + copy nearest reply | 3.20 | 3.24 | 4.72 | 4.36 | 3.88 | 28.0% |
| **agent** | **3.92** | 3.62 | **4.98** | **4.40** | **4.23** | 84.0% |

Retrieval ablation, both arms on one model, paired on the same 35 cases.

| dimension | with retrieval | without | difference | wins / losses |
|---|---:|---:|---:|---:|
| grounded | 4.66 | 2.31 | **+2.34** | 27 / 0 |
| voice | 4.77 | 3.09 | **+1.69** | 27 / 0 |
| actionable | 3.57 | 3.23 | +0.34 | 15 / 9 |
| postable | 0.66 | 0.86 | **−0.20** | 2 / 9 |

Three findings matter more than the headline.

**Escalation recall of 35.6% would block deployment.** The agent auto-handles
nearly two thirds of the cases that should reach a person. The cause is traceable
rather than mysterious: policy escalates outages unconditionally, but the
classifier recognises an outage in only 3 of 11 real cases, so the rule rarely
gets to fire. Classification failure causes the triage failure.

**Retrieval buys groundedness and voice, and nothing measurable elsewhere.** It is
worth +2.34 on groundedness with 27 wins and no losses. It is worth nothing on
actionability, and it actively makes replies *less* postable, because grounding in
real history is also how a placeholder token from this project's own
preprocessing gets copied into the output.

**The agent is not measurably more actionable than a one-line template.** 3.62
against 3.80, intervals overlapping. Two independent measurements agree on this,
so it is not a fluke of one comparison.

> ### Read this before using any number above
>
> The evaluation set is **not hand-labelled**. The human pass was abandoned after
> one item and the remaining 199 reference labels were generated by
> `gemini-3.1-flash-lite`. Every classification and escalation figure above is
> therefore **agreement between two models**, not accuracy against ground truth,
> and two models can agree confidently while both being wrong. The
> judge-versus-human agreement evidence the brief asks for is missing for the
> same reason. [Section 5 of the report](reports/REPORT.md) sets out exactly what
> this invalidates. The reply-quality and ablation results are scored against
> retrieved history rather than these labels and are unaffected.

## Reproduce in under a minute

Every model response is cached in `cache/llm/` and committed, so the reported
numbers recompute with no API key and no network.

```bash
make setup
make reproduce
```

To re-run against the live APIs, put `GROQ_API_KEY` and `GEMINI_API_KEY` in `.env`
and run `make predict && make judge`. Expect about an hour: the free tiers are
capped on tokens per day, not on requests.

## How it works

**Threads, not tweets.** The raw file is 3M individual tweets with reply pointers
and no conversations in it. `data.py` follows the pointers, then collapses runs of
consecutive tweets from one speaker into a single turn, because people send three
tweets in a row and that is one message.

**Split by date, not at random.** The same complaints recur on this account for
months. A random split would let the agent retrieve a near-duplicate of the case
it is being scored on. The cut at 2017-11-17 gives 11,091 retrievable history
cases and 3,697 held-out ones.

**One call, three outputs.** Intent, reply and proposed handling come from a
single structured call, because the reply depends on the intent and the escalation
reason has to agree with both. Separate calls could contradict each other.

**Two retrievers fused by rank.** BM25 over words catches the tokens that decide
the answer, since a Roku and a PlayStation need different steps. Character 3-5
grams survive "buffring" and "chromcast". Their scores are on incomparable scales,
so they are combined by reciprocal rank fusion. The pool excludes replies that
deflect to DM, so the agent cannot learn to stall.

**Escalation lives in code, not in the prompt.** The model proposes a handling
decision; `apply_policy` can override it. A policy inside a prompt cannot be unit
tested, cannot be audited, and changes silently when you swap models. The evidence
that this was right: across 31 cases that were accidentally generated twice at
temperature zero, the reply wording changed 71% of the time and the escalation
decision changed never.

**The judge has four guards.** Different vendor from the generator, blind to which
system wrote each reply, blind to the case's real answer so it scores quality
rather than similarity to one response, and a rubric anchored at 1, 3 and 5 because
unanchored scales drift to 4 for everything.

## Why Hulu

Brand choice was measured, not assumed, because it decides whether the reply half
of the project can be evaluated at all. A brand whose standard move is "please DM
us" resolves cases off-platform, so its public replies are handoffs and there is
nothing to ground a drafted reply in.

Counting both handoff idioms matters. A regex for "DM us" alone ranks AmazonHelp
as the most substantive brand in the dataset at a 0.7% deflection rate. Amazon
actually deflects by pasting a web-form link, and once channel-switch phrasing is
counted its rate rises to 12.1%.

| brand | outbound tweets | handoff rate | groundable replies |
|---|---:|---:|---:|
| hulu_support | 21,872 | 7.1% | 38.5% |
| AmazonHelp | 169,840 | 12.1% | 33.0% |
| AppleSupport | 106,860 | 54.1% | 32.6% |
| SpotifyCares | 43,265 | 31.1% | 27.5% |
| TMobileHelp | 34,317 | 82.9% | 4.5% |

Reproduce with `python scripts/01_brand_report.py`.

## Layout

```
src/agent/
  config.py      settings: model ids, rate budgets, paths
  data.py        thread reconstruction from the flat tweet dump
  taxonomy.py    the ten intents, boundary rules, escalation policy
  retrieve.py    BM25 + character TF-IDF over the brand's history
  agent.py       the classify / draft / triage call and the policy layer
  baselines.py   majority, keyword + nearest-neighbour, no-retrieval ablation
  judge.py       the reply-quality rubric
  evaluate.py    metrics, bootstrap intervals, agreement statistics
  llm.py         cached, rate-budgeted client for Groq and Gemini

scripts/         numbered pipeline stages, each runnable alone
data/golden/     the evaluation set, its labels, and the labelling interfaces
reports/         predictions, judgements, metrics, and the written report
cache/llm/       every model response, keyed by prompt hash
tests/           41 tests, including degenerate inputs a 3M-row scrape produces
```

## Models and the limits that shaped the code

The agent generates on Groq with `openai/gpt-oss-120b`. The judge scores on
Google's `gemini-3.5-flash-lite`. Reference labels come from
`gemini-3.1-flash-lite`. All three are deliberately different models, because a
judge from the generator's own family prefers its own phrasing and a labeller from
the agent's own family would agree with it for free.

Both free tiers bind, in opposite ways, and both shaped the client.

Groq caps **tokens per day** at 200,000, which appears in no response header. The
rate-limit headers report a healthy per-minute bucket and 993 remaining requests
while the daily budget is finished; the real limit surfaces only inside a 429
body. `llm.py` raises a distinct `QuotaExhausted` for it so a run stops with the
provider's own message instead of retrying into silence.

Gemini caps **requests per minute**, per model, and counts its daily allowance per
model too. The client keeps rolling per-provider budgets for both tokens and
requests, and reconciles its reservation against real usage after each call, which
took sustained throughput from one call a minute to over five.
